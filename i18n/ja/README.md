# codex-task-router

[English](../../README.md) · [日本語](README.md) · [简体中文](../zh-CN/README.md)

一つの Codex チャットで依頼を受け付け、適切なプロジェクト・担当チャットへ作業を振り分けるためのルール集です。`AGENTS.md` と、委託文・結果レポートの書式を収録しています。

以前、作業するセッションを取り違えたことがあり、依頼する場所を一つにまとめたいと思って作りました。

受付チャットは会話の文脈や一般知識で短く答えられる質問にはその場で答え、調査・分析・操作・成果物作成が必要な依頼を担当チャットへ委託します。依頼の原文・言語・資料を引き継ぎ、担当が保存したレポートをリンクで確認できます。作業が続いている間も、受付には次の依頼を送れます。

別案として、依頼が別セッション向けに見えるときに「中断」を推奨して確認する、[グローバル用の短いルール](../../session-scope-guard/README.md#日本語)も用意しています。

## 使い方

1. 依頼の受付に使うプロジェクトのルートへ、必要な言語版の `AGENTS.md` と `doc/results.md` をコピーします。`doc/` フォルダーの配置は保ってください。そのディレクトリを `codex-task-router` というローカル Codex プロジェクトとして登録し、チャットを開きます。
2. 対象プロジェクトまたは絶対パス、やってほしいこと、制約、必要なファイルやリンクを送ります。書き方は自由で、下の例に合わせる必要はありません。
3. 受付チャットが、依頼に合った既存の担当チャットを探します。新しく作る場合は、対象プロジェクト・作業範囲・モデル・推論レベルを提示し、[AGENTS.md](AGENTS.md) の承認ルールに従います。
4. 担当チャットが作業を進め、短いレポートを保存します。受付はレポートと担当チャットへのリンクを別々に案内し、次の依頼を受け付けます。

```text
対象: sample-app
依頼: 添付CSVの欠損値と重複行を確認してください。
制約: 元データは変更しない。結果は日本語。
資料1: 分析する元のCSV。
```

## 運用の要点

- Codex アプリの `list_threads`・`send_message_to_thread` とファイル操作ツールが使える環境が必要です。振り分けは文書を読んだ Codex が行います。常駐サービスやインストール用のスキルは含まれていません。
- 委託文と結果は、指定した言語、または依頼に使った言語で書かれます。依頼の原文と添付を保持し、担当が参照先にアクセスして読み取れることを確認します。
- モデルの選定方針は、特に難しい作業・高精度な PC 操作には Astra、主な作業には Sol、単純で明確な作業には Luna です。担当チャットの実際の設定・ツール・権限も確認し、既存の設定を黙って変えることはありません。
- 委託文とレポートの書式は [doc/results.md](doc/results.md) にあります。レポートの標準の保存先は `local/reports/`、一覧は `local/reports/README.md` です。送信先と送信状況は `local/routes.json` に記録します。
- 担当チャットは結果を保存し、受付へ完了メッセージを送りません。受付も結果待ちや自動回収は行わないため、確認したいときにレポートの表示を依頼します。独立した再検証は明示的に依頼した場合だけ行います。ツールの承認画面は担当チャットで操作します。
- レポートをブラウザで見たい場合は、HTML での表示を依頼できます。開けない場合は Markdown と成果物のリンクを案内し、表示は未確認であることを明記します。

## 構成

```text
AGENTS.md                 英語の委託方針
doc/results.md            英語の委託・結果書式
README.md / LICENSE / .gitignore
session-scope-guard/       グローバル用の短い別案（三言語）
i18n/ja/                  日本語版
  AGENTS.md
  doc/results.md
  README.md
i18n/zh-CN/               簡体字中国語版
  AGENTS.md
  doc/results.md
  README.md
```

標準は英語版です。別の言語を使う場合は、その言語の `AGENTS.md` と `doc/results.md` だけをコピーします。他言語版や README のコピーは不要です。

## 構成例

例えば、受付に Codex のサブスクリプションで GPT-6 Luna（`gpt-6-luna`）と推論レベル `max` を使う構成があります。モデルは別途設定してください。文書のコピーだけでは設定は変わりません。委託先のモデルは作業ごとに選びます。

## 関連する考え方

[OpenAI の dots](https://learn.chatgpt.com/docs/whats-new/dots-october-9-2026) には、既存の Codex スレッドを続けるか新しく作るかを判断し、追加指示を送るという共通点があります。[Meta の Muse](https://ai.meta.com/muse/) にも、会話で依頼を受け付け、複数のアプリを使って段階的に作業を進めるという、より広い意味での共通点があります。これは公開されている動作を比較したもので、内部の実装が同じという意味ではありません。このリポジトリはローカルの Codex チャット間の振り分けを扱い、どちらのサービスとも連携していません。

## 今後のメモ

[Jev API とローカルで動かせる Laya](https://unsloth.ai/docs/jp/moderu/decision-laya) を参考に、意思決定モデルで「実行モデル（ローカル／クラウド）→ 適切な既存セッション、または新規作成の提案 → 委託」を選ぶ構想があります。作業の難しさ・ツール・権限・進行中の作業を考慮し、現在の承認ルールを維持します。ローカルモデルでの実行と、この振り分けの仕組みは検討段階です。

[OpenAI Decisions API](https://developers.openai.com/api/docs/guides/decisions) の連携も候補です。2026年10月14日時点の公式資料では、[ChatGPT のプランを利用する経路](https://developers.openai.com/siwc/token-sharing-open-source/models-and-inference)は Responses API を使う方式で、Decisions API への対応は案内されていません。このリポジトリではまだ連携していません。
